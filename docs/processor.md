# Choosing a processor

Modular design is a key criterion for the construction of our TMC DCC command station. Philipp Gahtow’s [Z21PG](https://pgahtow.de/w/Zentrale_Z21PG/de) command station served as a shining example for us in this regard. This command station has a modular design and is compatible with several processors, such as the ATMega2560, ATMega328 and ESP32. The ATMega2560 appears to have by far the best support and is the most widely used.
However, as the ATMega2560 is a relatively expensive and outdated 8-bit processor, we wanted to replace it with a more modern and cheaper processor.

In the Z21PG command station, the various processors are controlled via “bit-banging” by the DCCInterfaceMaster library (https://github.com/Digital-MoBa/DCCInterfaceMaster). In this method, the processor’s output pins are set from so-called Interrupt Service Routines (ISRs).
 Although this method has the advantage of requiring little processor-specific code, our experience is that the library is relatively difficult to understand due to the large number of #ifdef constructs, and is therefore difficult to adapt. We therefore initially restructured and rewrote the “bit-banging” code from this library, and adapted the ATMega and ESP32 code accordingly. We then extended the code to support a number of new processors, such as the STM32, RP2040 and DxCore.

A disadvantage of “bit-banging” is that jitter of several microseconds can occur in the DCC signal. After rewriting the “bit-banging” code from the original library, we decided to try the following experiment: how easy or difficult would it be to completely rewrite the code from scratch, this time utilising the modern peripherals offered by the current generation of processors? In this step, we replaced the state machine that forms the core of the “bit-banging” code with an approach in which the entire DCC packet is calculated in advance, including the exact timing of all bits. We created implementations for DxCore, STM32, ESP32 and RP2040/2350 processors. During this experiment, we gained some insights that yielded results which were surprising to us. These insights are described below. We’ll start with the processor we consider least suitable for generating DCC, and conclude with the one we were most impressed by

## ESP32
We are somewhat disappointed with the ESP32. On paper, the so-called RMT timer is ideal for generating DCC signals and is therefore also used in projects such as DCC-EX and OpenRemise. Within a DCC packet, the RMT delivers an excellent DCC signal and there is no jitter.
 However, the problem arises between DCC packets. The combination of FreeRTOS, the relatively resource-intensive ESP-IDF hardware abstraction layer (HAL) and the (as far as DCC is concerned) inadequate IDF v5 RMT drivers (i.e. the current version) results in a significant delay when reconfiguring the RMT for the next packet. This delay is typically around 20 to 30 microseconds and is, moreover, not constant. Measurements show that the jitter averages around 2 microseconds but can rise to 7 microseconds or more; indeed, some online forums even report peak values of over 10 microseconds, particularly during Wi-Fi activity.
As this jitter occurs both between DCC packets and at the RailCom cut-out, the signal does not always comply with the DCC specifications. For this reason, we consider the ESP32 to be the least suitable for generating DCC signals.

## DxCore
The DxCore family performs considerably better; for example, the AVR64DA48, which can be regarded as the modern successor to the classic Arduino processors (ATMega 328, 2560). Here, we use TCA0 for the DCC signal and TCD0 (which usually remains unused) for the RailCom cut-out. As these processors do not support DMA, an interrupt is triggered after every DCC bit (116/200 µs), during which the timer registers are set for the next bit. In practice, this results in an extremely stable DCC signal with no jitter between packets. The RailCom cut-out timer is triggered in the ISR at the start of each packet, which means that, depending on other interrupts, some jitter may occur in the cut-out. Attempts to link the cutout timer entirely via hardware to the DCC timer (for example, via the event system) have not been successful in our tests. Nevertheless, the DCC signal itself is jitter-free, even though this is accompanied by a relatively high CPU load due to the numerous interrupts.

## STM32
The STM32 series consists of modern 32-bit microcontrollers and comprises a wide variety of variants. There are several families, such as the C, F, G and H families, and within each family there are a number of variants (such as the F1 and F4). Although all STM32s share a common basis, the variants differ considerably from one another, for example in terms of DMA architecture, caching, memory structure and available peripherals. In practice, this means that (Arduino) code is not simply interchangeable between different STM32 variants and that adaptations are often required for each variant. We have created implementations for the F4 and H7 series, in which we did not use FreeRTOS.
We used Timer 3 and DMA to generate the DCC signal and Timer 4 for the RailCom cut-out. The entire DCC packet is loaded into a DMA buffer in advance, so that signal generation is handled entirely by the hardware. An interrupt is required only at the end of each DCC packet to reconfigure the DMA channel, supplemented by Timer 4 interrupts at the start and end of the cutout.
As tens of microseconds are available per packet for this reconfiguration, there is effectively no jitter between consecutive DCC packets. For the RailCom cut-out function, a certain degree of jitter is theoretically possible, but in practice this proved to be not measurable, also because the interrupt priority is adjustable and can be optimised.
The result is a very stable and clean DCC signal with low CPU load, as only a limited number (3) of interrupts are required per packet.

## RP2040/RP2350
The biggest surprise for us were the RP2040 and the RP2350, known from the Raspberry Pi Pico.
Original Raspberry Pi Pico boards cost around 5 euros, and small boards are available from around 1.5 euros. The RP family consists of just two variants, which are largely software-compatible and feature an interesting peripheral: the PIO (Programmable IO). This is essentially a small, specialised coprocessor capable of generating very precisely clocked output signals. In combination with DMA, the entire DCC signal, including the RailCom cut-out, can be generated entirely by a single PIO (using two very simple state machines). Our RP implementation delivers an absolutely stable DCC signal without any jitter between packets or at the cut-out. Furthermore, the implementation is relatively straightforward and the CPU load is minimal: just one interrupt per packet. With a clock speed of 125 to 200 MHz and a dual-core architecture, the RP2040 also offers a great deal of processing power. In our opinion, the RP2040 is therefore the most suitable processor for generating DCC signals.
One drawback, however, is the relatively average quality of the ADC, which makes this processor less suitable for occupancy sensors, for example.

## Conclusion
Whilst the ESP32 disappoints due to its non-optimised RMT driver implementation and jitter issues, both DxCore and STM32 generate a good DCC signal, albeit with different trade-offs. The RP2040/2350, however, stands out: it offers the best DCC signal quality, the lowest CPU load, low cost and a relatively simple implementation. That is why we have opted for the RP2040/2350 in our command station.
